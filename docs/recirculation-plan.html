Recirculation Check

Six papers put chamber recirculation onset anywhere from under one second to thirty, and none of those numbers transfers to your stand. Record one long take, plot the level against time, read the knee. One function, one endpoint, one chart.

01 Why

The capture orchestrator sets PWM, stabilizes, records, then moves to the next step — the rotor never stops (capture_orchestrator.py:276). So the wake-development clock is not per-take; it runs for the whole 14.2-second sequence, and PWM ascends monotonically through it.

The structural problem

Accumulated recirculation is rank-correlated with your independent variable. Higher PWM means more air pumped and a dirtier room, and the high-thrust steps are the ones you care most about.

Before you re-run anything

All five material sets ran the same schedule to within 0.2 s, so the bias is largely common-mode. Material-vs-material comparison at a fixed step is far better protected than absolute levels or the PWM trend. This is not a reason to discard the campaign.

03 The whole feature

Already exists — nothing to build

POST /capture/acoustic accepts duration_seconds up to 120 s (capture.py:35), records every mic simultaneously and writes WAV + meta. The recording half of this feature is free.

What you do

  1. Set PWM to 2000
    Top of your campaign range — worst case, so the window you measure is conservative for everything below it. POST /tyto/pwm already exists.
  2. Press Record 60 s
    Calls /capture/acoustic with duration_seconds: 60 and trigger.enabled: false.
  3. Read the knee off the chart
    That is your clean window. Write it down.

What gets built

FileSizeWhat
server/core/recirculation.py ~30 lines One function — level_over_time(audio, sr). Frame the signal, band-RMS per frame, return times and per-band levels.
server/api/results.py ~20 lines GET /keys/{slug}/measurements/{id}/level_over_time — copies the existing /fft endpoint shape exactly.
src/components/setup/… 1 component Record button plus a line chart: level vs time, one trace per band.
What you are looking for read by eye

Four fixed bands — 100–500 / 500–2k / 2k–8k / 8k–20k Hz — so no blade-pass estimation is needed. Whichever band contains BPF is where the rise appears. Your eye finds this bend instantly and will not be fooled by a transient.

One thing not to get wrong

Turn trigger.enabled off. It defaults to true, and trigger-onset alignment shifts the start of the signal — which would corrupt the very time axis you are reading the onset from.

What survives is the only thing that mattered: the number, measured on your rig instead of borrowed from someone else's chamber. Everything else was scaffolding around it.

05 Two rig facts, found on the way

Neither blocks this feature any more, but both are true and worth knowing.

  • RPM is dead. rot_e reads 0.0 in all 275 stored takes. Harmless here because fixed bands don't need it — but it disables anything that wants blade-pass frequency.
  • Stabilization is a no-op. stabilize_rpm tests max(rpm) − min(rpm) < tolerance; with RPM pinned at zero that is always true, so it returns as soon as the sample window fills. That is the measured 0.3 s gap — every take records the spool-up transient, not steady state. A safeguard failing silently, which is the same failure class the papers are about.

06 Still open

Needs your answer

Is the space you measure in fixed? It blocks nothing here. But if the room can be moved or screened, a measured onset number becomes something to iterate against rather than live with.
